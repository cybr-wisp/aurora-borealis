# Day 9 — Evaluation protocol

Aurora's evaluation suite is deterministic and writes machine-readable results
under `experiments/results/`.

## Experiments

| Experiment | Primary outputs |
| --- | --- |
| Sensor noise sweep | RMSE, raw RMSE, NEES coverage |
| Sensor-count sweep | RMSE and fusion improvement |
| Packet-loss sweep | mean/p95 RMSE, NEES, percentage of runs below 5 m |
| EKF vs UKF turn | RMSE and NEES |
| Static-Q vs adaptive-Q maneuver | RMSE and recovery time |
| Crossing separation/noise | identity-switch phase diagram |
| Association scaling | p50/p95/p99 assignment latency |
| Ingestion overload | queue depth, shedding, p50/p95/p99 age |
| Adaptive R | detection delay, fixed/adaptive NIS, recovery |
| Degraded Monte Carlo | sub-5 m success rate and consistency |

## Run everything

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure

python experiments/run_all.py
```

The suite reuses Aurora's existing seeded radar and tracking implementations.
Plots are generated from result CSVs instead of containing hard-coded result
values.

## Interpretation rules

Do not claim a result until its corresponding artifact has been generated by a
run on the checked-in code.

Debug-build association latency must be labeled as Debug-build latency.

Hardware-in-the-loop results must remain separate from simulation-only results
until the physical ESP32 sensor node is connected and measured.
